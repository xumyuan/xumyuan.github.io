纹理 ​

纹理压缩 ​

BC 代表块压缩（Block Compression），即将纹理分块进行压缩。好处是更容易实现随机读取：只需要读取指定的块，而不需要全局解压。

BC1 ​

将纹理按 4×4 分块。假设在一个小块内，纹理的颜色变化是有限的。

同时假设在一个块内，颜色的变化在 RGB 空间是线性的。（这也会有问题：同一块的颜色可能差异较大。如果一个 4×4 的 block 中包含红色、蓝色、绿色三个像素，用 BC1 压缩后必然会有个颜色消失，因为这三种颜色在 RGB 空间中无法拟合成一条直线。）

压缩原理：

  • 4 字节 —— 从一块中找到两个颜色端点，每个颜色端点使用 2 字节存储，颜色通道分布为 5:6:5
  • 4 字节 —— 将颜色以上述端点划分为 4 段，即共有四种颜色可供块内的像素选择，每个像素需要 2 位索引，共 16×2/8=4 字节

透明度存储：

BC1 可以存储一位的透明度，即 0 或 255。

上述方法中，两端点的排布顺序并没有特别的要求，565 的颜色值还可以被解释为 16 位的整数，可以通过改变顺序的方式来存储透明度。

  • 如果第一个端点大于第二个端点，按上述方案存储
  • 如果第一个端点小于第二个端点，则颜色被等分为三段，第四段为黑色全透明。

这样做可能导致在常规双线性插值时，临界区域产生黑边。这可以通过将 alpha 阈值设置得高，从而剔除掉暗区，或者在着色器中将插值后的颜色除以插值后的 alpha 来避免，这将抵消变暗的效果。

BC4 ​

方案整体类似 BC1，但是只用于灰度图（高度图、光泽图等）。

两个端点各占 8 位，端点之间划分了 8 段，每个块内像素用三位编码。

透明度如果正序按上述方案，逆序则端点之间划分 6 段，剩余白色透明和黑色透明。

BC2、BC3、BC5 ​

这几个方案本质是前两个方案的组合。

BC3：

存储 RGBA 数据，使用 BC1 存储 RGB 通道，使用 BC4 存储 A 通道。块总大小为 16 字节，平均每像素 1 字节。是需要完整 Alpha 通道的纹理最常用的格式。或者用于将彩色纹理和灰度图打包。

BC5：

双通道格式数据，每个通道使用一个 BC4 存储。块总大小为 16 字节，平均每像素 1 字节。如果存储 X、Y 可以重建出 Z。适合切线空间的法线贴图。有更高的保真度，缺点是内存翻倍。

BC2：

存储 RGBA 数据，RGB 使用 BC1，Alpha 通道每像素使用固定的 4 位，即共代表 16 种不同的透明度。总大小和 BC3 一样，共 16 字节，但是效果不如 BC3，很少用。

ASTC ​

ASTC 同样是按块存储，每个块固定 16 字节，和块内的像素数量无关。块尺寸可选 4×4、5×4、5×5 等，块越大压缩率越高。

一次纹理大小的踩坑记录 ​

在接入 ASTC 纹理压缩库的时候，有一个计算压缩纹理大小的函数。但是这样计算的大小，不能正确的被 OpenGL 识别。

C++
uint32_t Texture::computeTextureSize(TextureFormat textureFormat, int width, int height)
{
    switch (textureFormat)
    {
    case TextureFormat::ASTC_4x4:
        return width * height * 16 / 16;
    case TextureFormat::ASTC_5x4:
        return width * height * 16 / 20;
    case TextureFormat::ASTC_5x5:
        return width * height * 16 / 25;
    case TextureFormat::ASTC_6x5:
        return width * height * 16 / 30;
    case TextureFormat::ASTC_6x6:
        return width * height * 16 / 36;
    case TextureFormat::ASTC_8x5:
        return width * height * 16 / 40;
    case TextureFormat::ASTC_8x6:
        return width * height * 16 / 48;
    case TextureFormat::ASTC_10x5:
        return width * height * 16 / 50;
    case TextureFormat::ASTC_10x6:
        return width * height * 16 / 60;
    case TextureFormat::ASTC_8x8:
        return width * height * 16 / 64;
    case TextureFormat::ASTC_10x8:
        return width * height * 16 / 80;
    case TextureFormat::ASTC_10x10:
        return width * height * 16 / 100;
    case TextureFormat::ASTC_12x10:
        return width * height * 16 / 120;
    case TextureFormat::ASTC_12x12:
        return width * height * 16 / 144;
    default:
    {
        uint8_t bitPerElement = computeBitsPerElement(textureFormat);
        return  width * height * bitPerElement / 8;
    }
    }
    return 0;
}

压缩透明度预乘 ​

预乘处理（Premultiplied Alpha）

原始 RGBA 像素：(R, G, B, A)

其中 RGB 是颜色值，A 是透明度（0=全透明，255=不透明）。

预乘后像素：(R×A, G×A, B×A, A)

将 RGB 通道的值乘以 Alpha 通道（归一化到 0-1 范围），再存储结果。

对图像进行预乘之后，可以将透明区域（透明度为 0）的 RGB 直接归零，再进行压缩处理。特别是 ASTC 这种有损的块压缩算法，能大大降低透明区域对块内像素颜色的干扰。

无透明度预乘对比有透明度预乘，左边没有预乘的有一个像素的白边。

Unity 的 Alpha Is Transparency ​

Unity的的贴图导入面板上有个开关，Alpha Is Transparency 这里的主要作用是让全透明像素的RGB值与最邻近的非透明像素保持一致，可以避免在双线性插值采样的时候，透明像素的RGB影响到非透明像素的RGB值（一般PS的处理会把全透明的像素做全白的处理，这会导致可能出现白边）。
