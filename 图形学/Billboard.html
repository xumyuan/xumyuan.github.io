Billboard ​

Billboard 根据相机调整平面朝向，常用于名字、血条、树、烟雾、火焰和 Sprite 粒子。几何通常还是一个四边形，变的是朝向，不是把平面变成球体。只绕指定轴旋转的 Billboard 仍可能在俯视、仰视时露出薄边。

场景里五个牌子站在同一条线上，可以观察固定平面、屏幕对齐和轴向约束的区别。演示中的标签是实现名称，不一定与各引擎的术语一一对应。

  • 普通 Quad：旋转写死，当对照组。
  • Sprite：Three.js Sprite 在渲染时按屏幕对齐方式展开。
  • Spherical：这里在 CPU 上使用 quaternion.copy(camera.quaternion)，实际属于屏幕对齐；不要把它与“法线指向相机位置”混为一谈。
  • Cylindrical：只绕世界 Y 轴转。树和名字牌常用，抬头低头时牌子不跟着躺倒。
  • GPU Expand：中心点变换到视空间后，直接给 xy 加四个角的偏移，这是屏幕对齐的一种实现。Cascade 普通 Sprite 的对应模式使用世界空间的相机基向量展开，几何效果等价，但代码用的不是这段视空间写法。

先分清：朝向规则与执行位置 ​

朝向规则平面的朝向需要的数据
屏幕对齐 Screen-aligned与相机成像平面平行相机 Right、Up
朝向相机位置 Point-facing法线指向相机位置粒子中心、相机位置、参考上方向
轴向约束 Cylindrical保持指定轴，只绕它转粒子中心、相机位置、锁定轴

规则决定“怎么算朝向”，CPU / Vertex Shader 决定“在哪里计算”。两者是独立的。CPU 模拟粒子，不代表 Billboard 的四个角也在 CPU 上展开。

后面的通用伪代码假设：局部 Quad 位于 XY 平面，+X 向右、+Y 向上、+Z 为正面；位置和方向都在同一世界空间。UE 使用 Z-up，Three.js 通常使用 Y-up，不能直接混用参考轴。叉乘顺序、UV 方向、三角形绕序需要与具体实现匹配。

顶点位置：中心加两根轴的偏移 ​

普通 Quad 的四个角可以用 (0,0)、(1,0)、(1,1)、(0,1) 表示。这里的二维坐标既能用作 UV，也能作为平面上的角点参数。

hlsl
float2 corner = uv - float2(0.5, 0.5);
float3 vertexWorld = center
    + right * width  * corner.x
    + up    * height * corner.y;

uv - 0.5 把 [0,1] 转成 [-0.5,0.5]，让粒子位置位于四边形中心。例如宽 100、高 60，四个角的偏移就是 ±50 * right ±30 * up。

不减 0.5 时，偏移范围是 [0,width] 和 [0,height]，粒子位置就位于一个角。更一般的写法是 corner = uv + pivotOffset，默认 pivotOffset = (-0.5,-0.5)。Pivot 改变旋转和缩放围绕的位置，不决定 Billboard 的朝向规则。

若要叠加粒子自身的平面内旋转，可以先旋转基向量，再用同一个展开公式：

hlsl
float s, c;
sincos(rotationRadians, s, c);
float3 rotatedRight = c * right + s * up;
float3 rotatedUp    = c * up    - s * right;
float3 vertexWorld = center
    + rotatedRight * width  * corner.x
    + rotatedUp    * height * corner.y;

屏幕对齐：直接使用相机的 Right / Up ​

hlsl
float3 right = cameraRight;
float3 up = cameraUp;
float3 vertexWorld = center
    + right * width  * (uv.x - 0.5)
    + up    * height * (uv.y - 0.5);

所有粒子的平面互相平行，也平行于屏幕平面。透视相机下，画面边缘粒子的法线不一定指向相机位置。

对于没有旋转父节点、位于局部 XY 平面的 Three.js 对象，在 CPU 上复制相机旋转也能得到这种效果：

js
object.quaternion.copy(camera.quaternion);

这里复制的是局部旋转。存在旋转父节点时，应先取相机世界旋转，再用对象父节点世界旋转的逆转换到对象局部空间；非均匀父级缩放还可能引入额外问题。Three.js 相机沿局部 -Z 观察，复制其旋转后，Quad 的局部 +Z 与相机世界 +Z 对齐，即与观察方向相反。

同样的屏幕对齐也能在视空间完成：

hlsl
// 使用列向量约定；centerWorld 已经是世界坐标。
float4 centerView = mul(viewMatrix, float4(centerWorld, 1));
float2 corner = uv - float2(0.5, 0.5);
float4 vertexView = centerView;
vertexView.xy += corner * float2(width, height);
float4 clipPosition = mul(projectionMatrix, vertexView);

所有角点保持相同的视空间 Z，只偏移 X/Y。四边形仍处于粒子中心所在的深度，只是与近平面平行，并没有贴到近平面上。宽高在投影之前应用，透视投影后仍然近大远小；固定像素大小的标签还需要按投影、深度和视口尺寸换算。

朝向相机位置：重新构造正交基 ​

先让法线指向相机，再用参考上方向确定平面内的朝向。只知道法线不足以确定完整旋转，因为平面仍可以绕法线自转。

hlsl
// 基础版本：要求相机不与中心重合，且 referenceUp 不平行于 normal。
float3 normal = normalize(cameraPosition - center);
float3 right  = normalize(cross(referenceUp, normal));
float3 up     = cross(normal, right);

float3 vertexWorld = center
    + right * width  * (uv.x - 0.5)
    + up    * height * (uv.y - 0.5);

referenceUp 可以选择相机 Up，也可以选择世界 Up。前者会参考相机侧倾，后者尽量保持相对世界的竖直朝向。不能直接把参考 Up 当作最终 Up，因为它未必垂直于法线。

同一粒子的所有角点必须使用由粒子中心算出的同一组轴。若每个角点根据“该角点到相机”的方向各算一组轴，通常就不是刚体旋转，会改变形状。

奇异点与数值退化 ​

  • 相机位置等于粒子中心：方向为零，朝向没有定义。
  • referenceUp 与法线平行或反平行：叉乘为零，无法确定 Right。
  • 接近平行：叉乘长度很小，微小输入误差会造成很大的朝向变化。

这不是欧拉角的万向节锁。即使用四元数存储结果，也不能自动补全缺失的参考方向。

这段伪代码加入了退化检测。positionEpsilon 应按场景单位设置，directionEpsilon 是方向叉乘长度的阈值：

hlsl
Basis BuildFacingBasis(float3 center, float3 cameraPosition,
                       float3 referenceUp, Basis fallbackBasis)
{
    float3 delta = cameraPosition - center;
    if (dot(delta, delta) < positionEpsilon * positionEpsilon)
        return fallbackBasis; // 上帧有效基，或相机的屏幕对齐基。

    float3 n = normalize(delta);
    float3 ref = normalize(referenceUp); // 调用方保证参考轴非零。
    float3 r = cross(ref, n);
    if (dot(r, r) < directionEpsilon * directionEpsilon)
    {
        // 选择与 n 最不平行的坐标轴。
        float3 a = abs(n);
        ref = (a.x <= a.y && a.x <= a.z) ? float3(1,0,0)
            : (a.y <= a.z) ? float3(0,1,0) : float3(0,0,1);
        r = cross(ref, n);
    }

    r = normalize(r);
    return Basis(r, cross(n, r), n);
}

这能避免零向量归一化，但切换参考轴仍可能产生跳变。要求动画连续时，可以将上一帧 Right 投影到新的朝向平面：r = previousRight - n * dot(previousRight,n)，检测有效后再归一化，最后计算 up = cross(n,r)。投影本身也可能退化，仍需备用方案；这种做法也不再严格保持指定的世界 Up。

Cylindrical：只绕指定轴转 ​

只绕坐标轴转时，可以先求“物体指向相机”的方向，把对应分量清零，再归一化。例如只绕 Y 轴转：

hlsl
// 原理伪代码，不是 Cascade 原码；假设清零后的方向非零。
float3 direction = cameraPosition - center;
direction.y = 0;
float3 normal = normalize(direction);

清零的是观察方向的 Y 分量，不是把旋转轴本身变成零向量。这样，法线只能在 XZ 平面里转，牌子不会因为相机上下移动而俯仰。在 Y-up 坐标系里，这就是保持竖直；UE 默认 Z-up，要绕世界竖直轴转，对应的是清零 Z 分量。

若绕的是任意方向的轴，就不能直接清零某个坐标分量，而要减去观察方向沿该轴的投影。以下伪代码假设 axisUp 已归一化：

hlsl
float3 delta = cameraPosition - center;
float3 horizontal = delta - axisUp * dot(delta, axisUp);
if (dot(horizontal, horizontal) < positionEpsilon * positionEpsilon)
    return previousBasis; // 相机位于锁定轴上，水平朝向没有定义。

float3 normal = normalize(horizontal);
float3 right  = normalize(cross(axisUp, normal));
float3 up     = axisUp;
// 再代入通用的顶点展开公式。

Three.js 中，世界 Y 为上方向、对象无复杂父级变换时，可以简写为：

js
const target = camera.position.clone();
target.y = object.position.y;
object.lookAt(target);

有父节点时需要统一世界坐标，并处理 target 与对象位置重合的情况。轴向 Billboard 适合保持竖直的树和标牌，但俯视时可能变薄，这是约束的结果。

Cascade 为什么不用显式清零？ ​

在本文核对的 UE 4.22.3 中，ParticleSpriteVertexFactory.ush:325 的绕轴旋转分支直接固定一根轴，再叉乘求另一根轴：

hlsl
float3 Right_AxisRot = SpriteVF.AxisLockRight.xyz;
float3 Up_AxisRot = -SafeNormalize(cross(Right_AxisRot,CameraDirection));

叉乘已经消除了观察方向沿锁定轴的分量。假设锁定轴为 A = (0,1,0)，观察方向为 D = (dx,dy,dz)，那么：

text
cross(A, D) = (dz, 0, -dx)

结果与 dy 无关，所以这里不需要先写 direction.y = 0。不过，这次叉乘算出的是平面内的另一根轴，并不是直接算出清零后的法线。

CPU 在 ParticleSystemRender.cpp:1323 调用 ComputeLockedAxes()，填入锁定轴，并为绕轴旋转模式选择这个 Shader 分支。这里说的是 EPAL_ROTATE_X/Y/Z；PSA_Velocity 在该版本中会优先进入速度对齐分支。

通用伪代码固定的是 up，Cascade 这里固定的是 Right_AxisRot，之后还会叠加粒子自转。因此两者可以用同一个投影原理理解，但轴的映射和最终计算不能逐行照搬。

相机恰好位于旋转轴上时，清零或去掉投影后会得到零向量，叉乘也会退化。前面伪代码中的“保持上一帧朝向”是一种处理建议，不是这段 Cascade 源码已有的逻辑。

这是旋转，还是重建 Mesh？ ​

对任意局部顶点 p，若使用同一组正交单位轴：

hlsl
float3 worldPosition = center + right * p.x + up * p.y + normal * p.z;

这等价于一个旋转矩阵乘以局部顶点，再加平移。使用列向量约定时，矩阵三列就是 right / up / normal；要构成纯旋转，还需保持一致的轴方向，使矩阵行列式为 +1。加入宽高后就是旋转加缩放。Quad 的局部 Z 为零，所以可以省略最后一项；任意三维 Mesh 不能直接省略，否则会被压扁。

Sprite 可以直接从参数和二维角点计算位置，不必保存一份带三维局部位置的独立 Mesh。它仍有预先确定的角点数量和三角形索引。普通 Vertex Shader 每次调用输出一个顶点，并没有将一个输入点扩增成四个顶点，也没有修改顶点之间的连接关系。

因此，“CPU 创建顶点缓冲”与“GPU 计算最终顶点位置”可以同时成立。后者通常只产生本次绘制的顶点输出，不会回写原始顶点缓冲。

Cascade：用真实源码对应计算流程 ​

这里核对的是 UE 4.22.3、提交 99a530d4ccbe6bea1e8f49df20acfeb294006962 的普通 Sprite 路径，不涉及 Mesh TypeData，也不能直接推广到所有版本的 GPU Sprite 实现。代码链接来自公开源码镜像。

1. CPU 初始化共享角点和索引 ​

ParticleResources.cpp:16 的 FParticleTexCoordVertexBuffer::InitRHI() 创建静态顶点缓冲，并填写：

cpp
Vertices[SpriteIndex*4 + 0] = FVector2D(0.0f, 0.0f);
Vertices[SpriteIndex*4 + 1] = FVector2D(0.0f, 1.0f);
Vertices[SpriteIndex*4 + 2] = FVector2D(1.0f, 1.0f);
Vertices[SpriteIndex*4 + 3] = FVector2D(1.0f, 0.0f);

同文件第 67 行的 FParticleIndexBuffer::InitRHI() 创建索引缓冲；第 81 行开始将每组角点连接为 (0,2,3)、(0,1,2) 两个三角形。这里生成的是基础二维角点和拓扑，不是每个粒子旋转后的三维四边形。

2. CPU 打包每个粒子的属性 ​

ParticleSystemRender.cpp:691 的 GetVertexAndIndexData() 中，相关赋值为：

cpp
FillVertex->Position = ParticlePosition;
FillVertex->OldPosition = ParticleOldPosition;
FillVertex->Size = GetParticleSizeWithUVFlipInSign(Particle, Size);
FillVertex->Rotation = Particle.Rotation;

这里的 Position 是粒子中心，还没有加四个角的偏移。尺寸的正负号用于编码 UV 翻转，Shader 展开几何时取尺寸绝对值。PSA_Square 等模式还会在 CPU 的 GetParticleSize() 中令 Y 尺寸等于 X。

ParticleVertexFactory.cpp:144 的顶点声明将二维角点设为逐顶点属性，在实例化路径中将中心、尺寸等设为逐实例属性。第 269 行的 InitStreams() 绑定共享角点缓冲。这样，同一粒子的所有角点共享一份粒子数据。

3. GPU 选择朝向轴，再叠加旋转 ​

ParticleSpriteVertexFactory.ush:308 的 GetTangents() 计算展开所需的两个轴。

Cascade 模式该版本的计算方式
PSA_Square / PSA_Rectangle无锁轴、无 HMD 修正时，使用相机 Right 和负的相机 Up，平行于屏幕平面
PSA_FacingCameraPosition用粒子到相机的方向与世界 Z 轴叉乘，朝向相机位置
PSA_Velocity使用位置差得到运动方向，再与观察方向叉乘；禁用粒子自身旋转角
锁轴模式使用锁定轴以及对应的朝向计算

FacingCameraPosition 的原始计算为：

hlsl
float3 CameraDirection = SafeNormalize(ResolvedView.WorldCameraOrigin - WorldPosition.xyz);
float3 Right_FacingCameraPosition = SafeNormalize(cross(CameraDirection,float3(0,0,1)));
float3 Up_FacingCameraPosition = cross(CameraDirection, Right_FacingCameraPosition);

源码的叉乘顺序和前面的通用约定不同，普通模式也使用负的相机 Up；需要结合 UV 方向和索引绕序理解，不能单独替换一个符号。源码中的 TangentUp 对应纹理 +V 方向，不一定是视觉上的“向上”。

选出基础轴后，第 370 行开始根据粒子角度计算 sincos，第 374 行执行：

hlsl
OutRight = SinRotation * Up_Square + CosRotation * Right_Square;
OutUp    = CosRotation * Up_Square - SinRotation * Right_Square;

该文件的 SafeNormalize 只限制分母，并未提供备用朝向，之后还有普通 normalize。因此，观察方向平行世界 Z 时的 FacingCameraPosition、运动方向平行观察方向时的速度对齐等，仍会退化，不能仅凭函数名就认为它能保证稳定性。

4. GPU 展开最终顶点 ​

ParticleSpriteVertexFactory.ush:468 的 GetVertexFactoryIntermediates() 先将粒子中心变换到世界空间，调用 GetTangents()，再执行以下原始代码：

hlsl
float4 VertexWorldPosition = float4(ParticleWorldPosition.xyz + ResolvedView.PreViewTranslation,1);
float2 Size = abs(Input.SizeRotSubImage.xy);
VertexWorldPosition += Size.x * (UVForPosition.x + SpriteVF.PivotOffset.x) * float4(Right,0);
VertexWorldPosition += Size.y * (UVForPosition.y + SpriteVF.PivotOffset.y) * float4(Up,0);

普通 Quad 的 UVForPosition 来自输入 TexCoord，默认 PivotOffset 为 (-0.5,-0.5)。PreViewTranslation 是为渲染精度而做的世界坐标平移，不是把粒子移到近平面。这里算的就是“中心 + 两根轴上的偏移”，之后才进行材质处理和投影。

此版本也支持 Cutout 几何：ComputeBillboardUVs() 可从预处理的轮廓缓冲取二维位置，顶点数不一定是 4，但仍使用相同的平面展开公式。

5. 非实例化路径也在 GPU 展开 ​

ParticleSystemRender.cpp:817 的非实例化路径循环写各个顶点：角点 UV 不同，但第 844 行仍然把每个顶点的 Position 都设为同一个 ParticlePosition。最终的三维角点偏移仍由上述 Shader 计算。

完整的数据流可以写成：

text
CPU 初始化：二维角点缓冲 + 三角形索引缓冲
CPU 每帧：中心、旧位置、尺寸、旋转角、颜色、SubUV 等粒子属性
GPU Vertex Shader：计算朝向轴 -> 叠加自转 -> 展开角点 -> 后续材质处理与投影
GPU 光栅化：按已有索引组成三角形并生成片元

和粒子工作怎么对上 ​

Billboard 解决“这张片怎么朝向当前视图”，不负责粒子的轨迹、寿命和颜色变化。Cascade 的常规模拟由模块更新粒子属性，再交给 Renderer / Vertex Factory；VAT 回放使用另一种数据来源，由着色器从贴图解码预烘焙的状态，Cascade 默认并不会自动从 VAT 取数据。

如果 VAT 保存的是中心、尺寸、自转等参数，回放时仍需要根据当前相机展开，常放在材质函数或自定义顶点逻辑里。若烘焙的是已经展开的顶点或完整朝向，则要明确是否还允许实时调整朝向，不能一概再套一遍 Billboard。

多视图、镜面 Capture 和 VR 中也需要区分当前渲染视图与主相机。若在 CPU 上只按主相机旋转一次，或者材质硬编码主相机方向，其他视图中的朝向可能不符合预期。在 Shader 中按当前 View 展开，可以为各视图分别计算；镜面效果是否需要特殊处理，取决于预期效果，不能统一关闭 Billboard。
