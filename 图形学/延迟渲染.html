延迟渲染 ​

延迟渲染的实质：

  • 先不做迭代三角形做光照计算，而是先找出你能看到的所有像素，再去迭代光照。就是先找出摄像机能看到的像素/顶点。
  • 直接迭代三角形的话，由于大量三角形是看不到的，会造成极大的浪费。就是说一些被遮挡的物体，以及几何体的背面之类的。

拆成两段看更清楚：

前向:  几何 → 立刻光照 → 颜色
延迟:  几何 → GBuffer → 统一光照 → 颜色
  • Geometry Pass：只画不透明几何，不做完整光照，把后续算光需要的量写进多张 RT（GBuffer）。深度测试保证每个屏幕像素最终只留下离相机最近的那个表面。
  • Lighting Pass：不再遍历三角形，而是遍历光源（或遍历屏幕像素再查灯），读 GBuffer 算光照，累加到 SceneColor。

复杂度从 O(物体像素 × 光源数) 变成 O(可见像素 × 影响该像素的光源数)。被挡住的几何只付了一次写 GBuffer 的钱，不会再为它们算光。灯再多，也只跟「屏幕上看得见的点」有关，跟场景里叠了多少层三角形无关。

前向里用 Z-Prepass 是这个思路的弱化版：只复用深度，真正着色时靠 Early-Z 杀掉被挡的 fragment。延迟更进一步，把法线、albedo、粗糙度也缓存下来，光照彻底从几何 pass 里拆出去。

延迟渲染VS前向渲染 ​

前向渲染：

  • 优点：
    • 支持半透明物体渲染
    • 支持使用多个光照pass
    • 支持每个物体单独计算光照，不同物体可以有不同的光照计算方式
  • 缺点：
    • 光源数量对计算复杂度影响巨大
    • 访问深度等数据需要额外的计算

延迟渲染：

  • 优点：
    • 在有大量光照的场景优势显著
    • 只渲染可见像素、节省计算量
    • 对后处理支持良好（GBuffer 里法线、深度现成，SSAO、SSR、延迟贴花都方便）
    • 用更少的shader
  • 缺点：
    • 不支持半透明物体（GBuffer 每个像素只能记一层表面）
    • 带宽占用大（多 RT 读写，高分辨率 / 移动端更明显）
    • 对MSAA支持不友好
    • 光照模型被 GBuffer 格式锁死，自定义材质要额外占通道

没有绝对谁更好：灯少、半透明多、要 MSAA、材质花样多 → 前向（或 Forward+）更合适；灯多、不透明为主、要大量屏幕空间效果 → 延迟更合适。 现代引擎基本是混合：不透明走延迟，半透明 / 特殊材质走前向。

GBuffer ​

GBuffer 是 Geometry Pass 写出来的一组 RT，Lighting Pass 只认这里面的数据，看不到原来的 mesh / 材质 shader。

UE 里大致是这样（详见 UE基础渲染管线）：

  • SceneColorDeferred：物体间接照明的数据
  • GBufferA：世界坐标下的法向量
  • GBufferB：材质属性（金属度、粗糙度、高光强度）
  • GBufferC：RGB 通道中保存了反照率（Albedo），alpha 通道中保存了环境光遮蔽（AO）系数
  • GBufferD：预烘焙的阴影值
  • GBufferE：由光照模型所决定的自定义数据（例如表面下散射的颜色，切空间向量等等）
  • Depth：用来反算世界位置，一般不单独再存一份 position

这也是「延迟光照不能随意逐片段」的原因：Lighting Pass 时几何已经没了，BRDF、各向异性、清漆、皮肤 SSS 想用额外数据，必须事先规划进 GBuffer，否则光照 shader 拿不到。不是不能逐像素算光，而是算光时只能看打包好的那几张图。

光照 ​

Draw Light Volume(绘制光源形状) ​

Draw Light Volume 的原理是，为每个光源影响范围建成 mesh，并绘制它们。往往是 1 个光源 1 次 draw call，并在 pixel shader 中计算本光源对该 pixel 的光照贡献，并以加法混合的形式叠加到 frame buffer 上。

如下图左为 spot light 的光源形状，下图右为 point light 的光源形状，它们都可以根据光源影响范围、张角等来调整对应光源形状模型的变换。

缺点：

  1. 过多的 draw call： n 个光源至少要 n 次 draw call，甚至有些方法是需要 2n 次。
  2. 另一种带宽开销：假设 n 个光源覆盖在同 1 个 pixel，那么计算该 pixel 的光照就需要读 n 次 G-Buffer，而在逐像素遍历光源策略中只需要读 1 次。

Tile-based Light Culling ​

Tiled-based Light Culling 将屏幕区分划分为多个 tile ，且每个 tile 拥有⼀个光源列表（包含所有在该 tile 内有影响的光源）。 这样就可以在对某个 fragment 着色时，算出该 fragment 所在的 tile，就能找到 tile 对应的光源列表，并对列表里的光源进行光照贡献计算，而不必对整个场景的所有光源进行光照贡献计算。 当相机或者光源的位置和方向发生改变时，所有的tile都需要重新计算。 缺点：

  • 基于屏幕空间的 tile 划分仍然粗糙，没有考虑到深度值（离摄像机远近的距离）划分。

如下图黑色线段物体，每个 shading point 本应该最多同时受到一个光源的影响，由于 tile 划分没有考虑 z 值，从而使得实际每个 shading point 都有三个光源的着色计算：

UE 里无阴影可见光源超过约 80 才会切 tiled deferred（tile setup 有固定开销，灯不够多不划算），低于这个数就每个光源一个 pass。详见 UE基础渲染管线。

Clustered / Forward+ ​

Tiled 只在 XY 切屏，Clustered 再沿深度把视锥切成格子，每个 3D cluster 一份灯列表，能避开上图那种「远近灯被塞进同一个 tile」的浪费。

Forward+（Tiled / Clustered Forward） 把这套 light culling 用回前向：几何还是物体自己的 shader 里着色，但每个 fragment 只算自己所在 tile/cluster 里的灯。灯多时接近延迟的扩展性，同时保住前向的材质多样性和半透明。和延迟的差别在于着色数据从哪来——Forward+ 当场从材质取，延迟从 GBuffer 取。

半透明 ​

延迟的 Geometry Pass 一般不画半透明。GBuffer 每个像素只能记一层表面，半透明需要多层颜色混合，塞不进去。

常见接法：不透明 + 光照做完之后，再按从后往前用前向画一遍半透明，读已经算完的 SceneColor / 深度做混合。交叉的半透明没有完美深度排序，要用加权混合、OIT 或拆成不交叉的 mesh，这是半透明本身的问题，不是延迟独有的，见 透明渲染。UE 把这套接法拆成 Standard / AfterDOF / Modulate 三个桶，见 [UE 半透明渲染](../Unreal Engine/半透明渲染.md)。

抗锯齿 ​

延迟不是不能抗锯齿，而是硬件 MSAA 很贵。

前向里 MSAA 只对 coverage / depth 按 sample 存，pixel shader 每个像素仍只跑一次，最后 resolve 平均，流程见 图形.md 的 MSAA 一节。延迟的 GBuffer 是「每像素一份材质」，要做 MSAA 就得按 sample 存法线、albedo、粗糙度……带宽直接乘 sample 数。所以一般不用硬件 MSAA，改走 TAA / FXAA，或者少数引擎做 MSAA deferred（按 sample 存 GBuffer，很吃带宽）。

后处理 ​

SSAO 需要位置和法线。延迟直接读 GBuffer 法线 + 深度反算位置。

前向没有 GBuffer，一般先画一张深度图，位置用深度反投影，法线用深度差分近似（质量不如 GBuffer 法线）。见 图形.md SSAO。
